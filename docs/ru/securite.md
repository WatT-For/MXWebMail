# Безопасность

*Переведено с французского - французская версия является исходной.*

## 1. Встроенная модель безопасности

### "Оставаться в системе" (персистентные токены)

Флажок "Оставаться в системе" выдаёт cookie `mxwm_remember`
(`selector:validator`, HttpOnly, Secure, SameSite=Lax, срок `remember_days`
- по умолчанию 30 дней). Таблица `auth_tokens` хранит только **SHA-256-хэш**
валидатора; он **ротируется при каждом использовании** (украденная cookie,
уже предъявленная, обнаруживается и аннулируется). Восстановление заново
расшифровывает IMAP-пароль (`CredentialCrypt`) и заново проверяет учётные
данные - неудача удаляет токен. Каждый токен фиксирует **IP при выпуске**
(`ip`), **последний известный IP** (`last_ip`, при каждом восстановлении) и
User-Agent - видны в Настройки > Сессии для обнаружения незнакомой сессии.
Токены там перечислены и отзываемы, а текущий токен отзывается при
**ручном** выходе (выход по неактивности `autologout` его сохраняет: сессия
восстанавливается молча при следующем визите). Любая новая сессия (обычный
вход или восстановление) открывается на последнем использованном аккаунте -
с возвратом к аккаунту по умолчанию.

### CSRF

Каждый POST требует CSRF-токен сессии (`X-CSRF-Token`, поле формы или ключ
JSON); API плагинов (`/api/plugin/…`) требуют его независимо от HTTP-метода.
Второй слой, основанный на заголовках **`Sec-Fetch-*`**, отклоняет
cross-site запросы кроме GET-навигации к документу - даже без активации
пользователя, поскольку браузер убирает `Sec-Fetch-User` после каждого
редиректа (порталы, переписанные ссылки) (`secfetch_allow` позволяет
расширить эти правила).

### HTTP-заголовки

`X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`,
`Referrer-Policy: strict-origin-when-cross-origin`, опциональный HSTS и
**CSP** с nonce на запрос (директива `script-src` включает `unsafe-eval`,
требуемый Knockout). Вложения, отдаваемые inline, получают
`Content-Security-Policy: sandbox`.

### Шифрование учётных данных

IMAP-пароли (и секреты плагинов) шифруются **XSalsa20-Poly1305**
(`sodium_crypto_secretbox`, libsodium) мастер-ключом `app/storage/app.key`,
в сессии и в базе. См. [base-de-donnees.md](base-de-donnees.md).

### Дополнительные аккаунты OAuth2

Публичные домены (Gmail, Outlook, Yahoo - см. [domaines.md](domaines.md))
добавляются через **authorization code + PKCE**: `state` anti-CSRF и verifier
хранятся в сессии, `redirect_uri` реконструируется на стороне сервера (host
фильтруется как `force_https`). Только *refresh token* персистируется,
зашифрованный как пароль; эфемерный *access token* существует только в
памяти на время подключения (XOAUTH2/OAUTHBEARER). Ротация refresh token
(Microsoft, Yahoo) повторно применяется в базе при каждом обмене. Email из
`id_token` служит контролем согласованности; доказательством принадлежности
остаётся само OAuth-IMAP-подключение. Callback (`/api/oauth/callback`)
возвращает только мини-страницу `postMessage`>`window.close()` для
popup согласия.

Учётные данные OAuth2-приложения - **по пользователю** (таблица
`oauth_apps`, вводятся при первом добавлении аккаунта или в настройках):
`secret` шифруется тем же мастер-ключом и никогда не возвращается в
интерфейс. Удалённое или изменённое приложение инвалидирует зависящие от
него аккаунты (refresh token остаётся привязан к исходному client_id).

### Rate-limit при входе

`login_max_attempts` (5) затем блокировка `login_lock_seconds` (300 с).
Счётчик персистируется в `storage/cache/login_attempts.json` (ключ
`sha256(IP|login)`, очистка записей неактивных > 1 ч, запись под `flock`).
Активная блокировка ни продлевается, ни перезаписывается отклонёнными
попытками (429). Применяется и ко входу админа. Журнал аутентификации в
стиле fail2ban доступен (`auth_logging*`, плейсхолдеры `{request:ip}`,
`{imap:login}`, `{result}`; CR/LF нейтрализованы): покрывает входы webmail и
админа (логин с префиксом `admin:`) и ошибки кода TOTP. Полная интеграция:
[fail2ban.md](fail2ban.md).

### Санитизация HTML сообщений

Тело сообщений санитизируется в браузере (инертный DOMParser + allowlist):
ограниченные теги и атрибуты (без `script`/`iframe`/`object`/`on*`…),
блокировка схем `javascript:`/`vbscript:`/`data:`, нейтрализация коварных
стилей (`position:fixed`, скрытое содержимое), префиксация классов. CSP -
второй слой.

### Отправка сообщений

- **From**: строгий whitelist - адрес аккаунта или объявленная идентичность
  (IDN принимается в обеих формах); любое другое значение отклоняется (403).
- **Получатели**: поля To/Cc/Bcc проходят строгий разбор - недействительный
  сегмент не отбрасывается молча, отправка отклоняется (400) со списком
  непонятых адресов.
- **CR/LF**: нейтрализованы в теме, заголовках трединга (In-Reply-To,
  References), упомянутых именах папок и MIME-параметрах вложений
  (`filename=`).
- **Bcc**: заголовок удаляется из данных, отправляемых SMTP-серверу, но
  сохраняется в копии "Отправленные" (виден только отправителю).
- **Редактор**: iframe TinyMCE несёт `Content-Security-Policy`, блокирующую
  любую удалённую загрузку - содержимое пересланного/вставленного сообщения
  не может эксфильтровать подтверждение прочтения при открытии.
- **Временные вложения**: токены с областью пользователя, имя санитизовано
  (`basename` + управляющие символы удалены), очистка через 24 ч.
- **Ошибки SMTP**: клиент получает общее сообщение; сырые ответы сервера
  раскрываются только если `labs.smtp_show_server_errors` включён
  (диагностика, может раскрывать внутренние детали).

### OpenPGP

Шифрование/расшифровка происходит **целиком в браузере** (OpenPGP.js).
Сервер хранит только armored-связку; приватные ключи защищены их passphrase
и никогда не расшифровываются на стороне сервера. **Шифруется только тело
сообщения**: отправка вложений отклоняется при включённом шифровании (они
ушли бы открытым текстом).

### Прокси изображений

Удалённые изображения проходят через `/api/proxy`: только `http(s)`,
опциональный allowlist (wildcards), **anti-SSRF** (отклонение
приватных/зарезервированных IP, ревалидация на **каждом** редиректе - макс.
3), таймаут, ограниченный размер. Реальный MIME тела проверяется по
**bitmap-allowlist** (png, jpeg, gif, webp, avif, bmp, ico) - SVG и любой
активный тип отклоняются - и ответ несёт
`Content-Security-Policy: sandbox` + `nosniff`. Журналы хранят только
scheme+host+путь (никогда query, которая может содержать токены).

### Управление IP и прокси

`X-Forwarded-For`/`X-Forwarded-Proto` учитываются только если `REMOTE_ADDR`
входит в `trusted_proxies` (CIDR). Детекция HTTPS (`isHttps`) следует тому
же правилу.

## 2. Рекомендации по усилению

- **Document root = `public/`** только; никогда не направляйте на корень
  проекта. Приватные папки (`app/`, `config/`, `storage/`…) имеют свои
  защитные `.htaccess`, но это лишь запасная сеть.
- **HTTPS обязателен**: включите `force_https` + `hsts` в продакшене.
- **За обратным прокси** (Nginx, HAProxy, Cloudflare…): заполните
  `trusted_proxies`, чтобы сделать надёжными rate-limit, allowlist и
  журналы; без этого любой `X-Forwarded-*` игнорируется.
- **Ограничьте админа**: `admin_ip_allowlist` (IP/CIDR CSV) и нетривиальный
  `admin_path`; включите **TOTP админа** через плагин `two-factor-auth`
  (секрет `admin_totp_secret` требуется только пока плагин активен).
- **Локальный админ-аккаунт**: предпочтительнее `admin_user` +
  `admin_password_hash` (сильный пароль), чем IMAP-fallback для
  администрирования.
- **Копия `app.key`** вне webroot; никогда не версионируйте.
- **`debug = false`** в продакшене (не раскрывать внутренние ошибки).
- **Мастер `/setup`** встроен в ядро: отвечает 404 после установки
  блокировки `app/storage/INSTALLED` - больше никакого установочного файла
  в webroot.
- Проверьте `ssl.verify_certificate`: `false` допустимо только для
  контролируемых самоподписанных сертификатов.
- В режиме обслуживания `maintenance = true` отдаёт выделенную страницу
  обслуживания в 503 на `/` (подключённые пользователи переключаются на
  неё при следующем API-запросе, сессия сохраняется) и перекрывает
  `/api/*` пользователя (админ и `/api/ping` остаются активными).

## 3. Известные ограничения

- Репозиторий `GitHubClient::REPO` заперт на `WatT-For/MXWebMail`:
  устанавливаемые пакеты (zip ядра релиза, файлы плагинов, читаемые в репо
  на ref `update.plugins_ref` через git-API + `raw.githubusercontent.com`,
  каждый проверен по sha1 git-blob) приходят только из этого репозитория -
  никакой произвольный URL не конфигурируется. Пакет ядра проверяется на
  двух уровнях: сумма sha256 ассета (файл `<zip>.sha256` релиза), затем
  `files.sha256` (встроенный помодульный манифест, контролируется после
  распаковки); константы `APP_REQ_PHP`/`APP_REQ_FROM` `App.php` пакета
  декларируют требования (версия PHP, минимальная исходная версия),
  применяемые до копирования. Официальный репо **публичный**: API, ассеты и
  `raw` работают без токена (анонимная квота API GitHub покрывается кэшем
  `cache.update_ttl`). Опциональный GitHub PAT (доступ `Contents: Read` к
  репо), настроенный в `config.php`, может поднять квоту или обслуживать
  приватный форк через `update.repo` - ассеты тогда отдаются через эндпоинт
  `releases/assets/<id>` (`browser_download_url` отдаёт 404 на приватном репо
  даже аутентифицировано). `update.plugins_local` и `update.manifest_url`
  (альтернативный манифест релиза) зарезервированы для dev/тестов -
  изменяются только через `config.php`, никогда через API админа. Во время
  копирования файлов флаг `storage/update/applying` перекрывает API
  пользователя (503, истекает через 15 мин).
- Смена SQLite > MariaDB не мигрирует данные (чистая схема).
- Приватные ключи OpenPGP хранятся armored на стороне сервера (passphrase
  защищает сам ключ, без дополнительной инкапсуляции).
